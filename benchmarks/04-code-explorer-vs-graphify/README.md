# Case Study 04: Comparative Evaluation of `CodeExplorer` (`ce`) vs. `graphify` (`graphifyy`)

> **Scope & Impartiality Disclosure**: This benchmark evaluates two open-source Model Context Protocol (MCP) codebase graph engines—**`CodeExplorer` (`ce` `v1.75.0`)** and **`graphify` (`graphifyy` `v0.9.104`, `safishamsi/graphify`)**—across the same two open-source TypeScript/polyglot monorepos and frozen ground-truth dataset used in [Case Study 03](../03-code-explorer-vs-codebase-memory-mcp/README.md) (`twentyhq/twenty` at `24,527` tracked files / `~2.49M` LOC and `immich-app/immich` at `3,205` tracked files / `~461k` LOC).
>
> Because the two tools have fundamentally different architectures and goals—**`graphify`** is a Python + Tree-sitter + NetworkX structural knowledge-graph builder with Leiden community detection, docstring rationale extraction, and optional LLM multimodal synthesis (`graphify-out/graph.json`), whereas **`ce`** is a compiled .NET 10 **Layer 1–5 semantic and global architectural ontology engine** backed by SQLite and an OpenCypher compiler—we divide the evaluation into three distinct parts:
> 1. **Part 1 — Head-to-Head on Common Ground (`C1`, `C2`, `C6`, `C7` + Cold Indexing Speed & Scalability):** Direct competition on structural and call-graph capabilities (`130` deterministically sampled ground-truth items).
> 2. **Part 2 — Extended L4/L5 Architectural Capabilities (`C3`, `C4`, `C5`, `C8`, `C9`, `C10`, `C11`):** Evaluation of `ce` (and `graphify`'s SQL/manifest extractors where applicable) on message queues, ORM database tables, code-to-table read/write lineage, and monorepo sub-project boundaries (`235` ground-truth items).
> 3. **Part 3 — MCP Server Tool Surface, Cold Startup, Warm Stdio Latency & Agent Ergonomics:** Comparison of the MCP tools and resources exposed to AI agents (`36` tools in `ce` vs. `10` tools + `6` resources in `graphify`), cold MCP initialization latency, memory footprint, and warm JSON-RPC round-trip latency.

#### Why `ce` (`147.33 s`) Scales to 24.5k-File Monorepos While `graphify` (`>45 min`) Stalls
1. **Single-Pass AST & Framework Analysis in `ce` (`51 s` on `twenty`):**
   - `ce` orders the 46 packages in `twenty` by dependency (`twenty-shared` and `twenty-ui` before `twenty-front` and `twenty-server`) and parses each file's AST and framework constructs in a single pass (`51 s` total for `36,644` files on `twenty`), finishing the full 5-layer cold index in **`147.33 s`**.
2. **Bottlenecks in `graphify` (`v0.9.104`) on Large TypeScript Monorepos:**
   - **Slow `detect()` Phase (`117.1 s` on `twenty`):** Before parsing ASTs, `graphify`'s `detect()` phase spends `117.1 s` walking and classifying files on `twenty`.
   - **Duplicate Single-Threaded JS/TS Re-Parsing:** After `ProcessPoolExecutor` workers finish extracting `per_file` ASTs (~`415 s`), `_collect_js_symbol_resolution_facts` re-parses all `24,048` JS/TS files a second time sequentially on a single Python thread.
   - **Quadratic Symbol Resolution Loop:** `_apply_symbol_resolution_facts` scans the node list linearly for each symbol reference (`>200,000` uses across `~300,000` nodes on a single CPU core).

#### Detailed Analysis of Part 1 Differences
1. **Call Graph Resolution & Nested Arrow-Function Granularity (`C6`: Tie `100` vs. `100` on `immich`, `ce` `100` on `twenty`):**
   - Both **`ce`** (`20/20` on `immich`, `12/12` on `twenty`) and **`graphify`** (`20/20` on `immich`) achieve **100% recall** on `C6`, resolving both intra-class helper calls (`this.helper()`) and cross-file NestJS constructor-injected service calls (`this.service.method()`).
   - **Important Structural Granularity Difference (`[:DECLARES]`):** When a method declares an inline arrow function or callback inside an object literal (e.g., `hooks: { configureImmichDatabaseDump: (d) => this.configureImmichDatabaseDump(d) }` in `futo-backups.service.ts:40`, `handlers = { [SyncRequestType.AssetsV1]: () => this.syncAssetsV1() }` in `sync.service.ts:191–192`, or `startStream: async () => { await this.agentTurnRecorderService.markRunning(...) }` in `agent-chat-streaming.service.ts:156–170`), `graphify` flattens the call directly onto the outer method (`updateLibraryConfig`, `streamInternal`, `retryLastFailedTurn`), whereas **`ce` models the nested arrow function as a distinct child `:Function` node** (`hooks.configureImmichDatabaseDump`, `handlers.[SyncRequestType.AssetsV1]`, `started.startStream`) linked to the enclosing method via `(:Function)-[:DECLARES]->(:Function)-[:CALLS]->(:Function)`. Traversing `OPTIONAL MATCH (enclosing:Function)-[:DECLARES]->(caller)` recovers 100% (`20/20` and `12/12`) of enclosing method names while preserving lambda-level call attribution.
2. **Incoming & Outbound HTTP Endpoints (`C1` and `C2`):**
   - **`C1` (Incoming Endpoints):** `ce` synthesizes first-class `:Endpoint` nodes carrying both the HTTP verb (`GET`, `POST`, `DELETE`) and the full resolved URL route template (`/api/albums/:id`, `/api/assets`), scoring **`100` (`20/20`) on both `immich` and `twenty`**. `graphify` has no `Endpoint` or `Route` ontology concept (`0/20` strict recall), though it does record `3,082` generic `references` edges with `context="decorator"` on `immich` (of which `354` point to `@Get`/`@Post`/`@Put`/`@Delete`, matching the line locations of all `20/20` sampled handlers without any route path or HTTP method metadata).
   - **`C2` (Outbound HTTP Calls):** `ce` scores **`83` (`5/6`) on `immich`** and **`50` (`6/12`) on `twenty`** via its `:ExternalService` and `:CALLS_ENDPOINT` extractors (`fetch`, `axios`, SDK clients). `graphify` does not model outbound HTTP/REST calls (`0/6` and `0/12`).
3. **Class Inheritance & Interfaces (`C7` — Tie `15` vs. `15` on `immich`, `ce` `80` on `twenty`):**
   - On `immich`, both tools tie at **`3 / 20` (`15` Recall)** because 17 of the 20 sampled classes use external functional mixin calls (`export class BulkIdsDto extends createZodDto(Schema) {}` where `createZodDto` is imported from the external npm package `nestjs-zod`). Note that `graphify` extracts `1,560` total heritage links on `immich` because it also extracts Dart `extends`/`with`/`implements` in `mobile/lib/` (`State<T>`, `ConsumerState<T>`, `ChangeNotifier`) and `tsconfig.json` `extends` edges.
   - On `twenty`, `ce` achieves **`80` (`16/20`, up from `65` in `v1.74.0`)** thanks to topological project sorting resolving cross-package base classes (`twenty-shared` $\to$ `twenty-server`).

## 6. Impartial Summary of Trade-Offs

### 6.1 Where `graphify` (`v0.9.104`) Excels
1. **High-Recall TypeScript Intra-Class & DI Call Graph on Small/Medium Repos (`C6`: Tie `100` vs. `100` on `immich`):** On `immich`, `graphify`'s `resolve_ts_member_calls` resolved 100% (`20/20`) of sampled intra-class and constructor-injected service method calls with a compact edge set (`49` target edges).
2. **Unsupervised Leiden Community Detection & "Surprise" Bridge Analysis:** `graphify` clusters code graphs into communities (`896` on `immich`) using the Leiden algorithm and surfaces cross-community architectural bridges (`graphify://surprises`), auto-generated architectural questions (`graphify://questions`), and `rationale` nodes extracted from docstrings/comments (`# WHY:`, `# NOTE:`).
3. **GitHub PR Triage (`list_prs`, `get_pr_impact`, `triage_prs`) & Knowledge Vault Exports:** `graphify` includes built-in MCP tools to fetch open GitHub PRs and rank them by structural blast radius, as well as exporters for Obsidian vaults, Wikipedia-style markdown articles, and interactive HTML graphs.

### 6.2 Where `CodeExplorer` (`ce` `v1.75.0`) Excels
1. **Order-of-Magnitude Faster Indexing & Monorepo Scalability (`6.1×` faster on `immich`, `>18.6×` faster on `twenty`):** `ce` indexes `immich` in **`17.60 s`** (vs. `graphify`'s `107.60 s`) and `twenty` (`24,527` tracked files) in **`147.33 s`** (`456,711` nodes, `960,660` edges), whereas `graphify` stalls for **>45 minutes** in single-threaded JS/TS re-parsing and $O(|\text{uses}| \times |\text{nodes}|)$ symbol resolution.
2. **Rich L4/L5 Architectural Ontology (`97` Micro-Recall in Part 2, `100` on `C1` Endpoints & `50–83` on `C2` Outbound HTTP):** `ce` models REST/GraphQL/FastAPI endpoints with full URL routes and HTTP verbs, outbound HTTP calls, BullMQ producers and consumers, TypeORM/Kysely database tables, code-to-table `READS_FROM`/`WRITES_TO` lineage (`17,382` edges on `twenty`), and monorepo sub-project boundaries.
3. **6.2× Faster Cold MCP Startup, 2.5× Lower RAM, and 8–43× Faster Search & Path Queries:** Because `ce` queries an indexed SQLite database rather than deserializing a multi-megabyte JSON file into NetworkX on startup, `ce mcp` initializes in **`608 ms`** (`64.2 MB` RSS vs. `3,782 ms` and `162.7 MB` RSS for `graphify`), resolves multi-match symbols (`validate`, `AuthService`) in a single round trip without ambiguity errors, and executes OpenCypher queries in **`3.1–3.8 ms`**.

### 6.3 Methodological Note: Deterministic Static Extraction (`--code-only`) vs. Optional LLM Synthesis
`graphify` offers two extraction stages: a deterministic Tree-sitter + NetworkX static pass (`extract --code-only`, which handles all source code files by default) and an optional LLM subagent pass intended primarily for unstructured documents, PDFs, images, and conceptual links (`SEMANTICALLY_SIMILAR`, `CONCEPTUALLY_RELATED`). Both tools were evaluated in their deterministic, zero-LLM static analysis modes for three reasons:
1. **`graphify` Stalls in the Static AST Pass Before Any LLM Pass Begins:** On `twenty` (`24,527` files), `graphify` hangs for `>45 minutes` inside `extractors/resolution.py` during the deterministic AST symbol-resolution phase, before any optional LLM stage could ever execute.
2. **Economics & CI Reproducibility at Scale:** Running LLM subagents across `24,527` files (`~2.49M` LOC) would cost tens to hundreds of dollars per full index and require hours of API calls, whereas `ce` extracts `456,711` nodes, `960,660` edges, `164` ORM tables, and `17,382` `READS_FROM`/`WRITES_TO` lineage edges deterministically in **`147.33 s` for `$0.00`**.
3. **Strict Architectural Lineage vs. Probabilistic Conceptual Edges:** Answering whether a method writes to a database table (`WRITES_TO`) or publishes to a BullMQ queue (`PUBLISHED_BY`) requires exact AST/decorator/ORM type resolution (`100%` deterministic precision), not probabilistic LLM-inferred `AMBIGUOUS` / `CONCEPTUALLY_RELATED` edges.
